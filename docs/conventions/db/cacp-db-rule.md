# cacp项目数据库设计规范
## 概述

本规范适用于 cacp项目数据库设计，确保数据库对象命名统一、结构合理、可维护性强。

---

# 一、命名约束

## 1.1 基本规则

| 序号 | 规则 | 示例 |
|------|------|------|
| 1 | 数据库对象名由字母、数字、下划线 `_` 组成，**以英文字母开头** | `USER_INFO` ✓ |
| 2 | 单词间通过下划线 `_` 连接 | `ORDER_DETAIL` ✓ |
| 3 | **不得使用数据库保留字、关键字** | 禁止：`DATE`、`RANK`、`ORDER`、`LIMIT`、`VALUE` |
| 4 | **不得使用双引号包裹命名** | `CREATE TABLE HEPS_EVENT_BAK` ✓ |
| 5 | **不得使用汉语拼音或首字母缩写** | `YONGHU` ✗ → `USER` |
| 6 | **统一大写** | `USER_INFO` |
| 7 | 表名应包含应用简称，能表达业务含义 | `HEPS_ORDER` |
| 8 | **长度限制 40 个字符以内** | |

## 1.2 表命名规范

| 类型 | 命名规则 | 示例 |
|------|----------|------|
| 预录入表 | `PRE_` 前缀 | `PRE_DECL_ORDER` |
| 执法表 | `CUR_` 前缀（电子口岸专网） | `CUR_CHECK_RESULT` |
| 参数表 | `PARA_` 前缀 | `PARA_TAX_TYPE` |
| 其他系统表 | `COPY_应用名_` 前缀 | `COPY_H2K_CONTRACT` |
| 表头表 | `_HEAD` 后缀 | `ORDER_HEAD` |
| 表体表 | `_LIST` 后缀 | `ORDER_LIST` |
| 日志表 | `_LOG` 后缀 | `OPERATION_LOG` |
| 临时表 | `_TMP` 后缀 | `EVENT_TMP` |
| 异常表 | `_EXCEPTION` 后缀 | `EVENT_EXCEPTION` |
| 备份表 | `_BAK` 后缀 | `EVENT_BAK` |

## 1.3 字段命名规范

| 规则 | 描述 | 示例 |
|------|------|------|
| 业务含义 | 字段命名应能表达业务含义 | `USER_NAME`（用户名） |
| 日期字段 | 以 `DATE` 后缀 | `DECL_DATE`（申报日期） |
| 时间字段 | 以 `TIME` 后缀 | `REC_CREATE_TIME`（记录生成时间） |
| 同义异名 | 全系统范围内避免，关联表字段命名要一致 | |
| 同名异义 | 全系统范围内避免，通过增加定语区分 | |

## 1.4 索引与对象命名

| 对象类型 | 命名格式 | 示例 |
|----------|----------|------|
| 主键 | `PK_表名` | `PK_USER_INFO` |
| 唯一索引 | `UK_表名`（多个以数字区分） | `UK_USER_INFO_1` |
| 普通索引 | `IX_表名`（多个以数字区分） | `IX_ORDER_LIST_1` |
| 序列 | `SEQ_` 开头 | `SEQ_USER_ID` |
| 存储过程 | `PROC_` 开头 | `PROC_GET_ORDER` |
| 函数 | `FN_` 开头 | `FN_CALC_AMOUNT` |
| 视图 | `V_` 开头 | `V_ORDER_SUMMARY` |

# 二、主键约束

| 序号 | 规则 |
|------|------|
| 21 | 数据表应含有主键（不涉及业务、不做双中心数据同步的技术日志表除外），**主键值不得直接修改** |
| 22 | 需使用自增列做主键时，**自增步长应设为 2**；自增列**不能有业务含义**（业务网） |
| 23 | **不得单独使用带有自动更新属性的时间戳** `ON UPDATE CURRENT_TIMESTAMP(6)` 作为主键 |
| 24 | 数据量增长较快的表应分区，如表数据量**超过 2000 万条时设计分区** |
| 25 | 分区表的主键、索引应建成本地索引 |

# 三、必备字段约束

每张表必须包含以下三个字段：

| 字段名 | 含义 | 类型 | 说明 |
|--------|------|------|------|
| `REC_VERSION` | 版本号 | 整型（默认 0） | 每次数据更新时字段值 +1 |
| `REC_CREATE_TIME` / `INDB_TIME` | 入库时间 | 时间类型 | 缺省值为数据入库时的系统时间 |
| `REC_LAST_UPDATE_TIME` / `UPDATE_TIME` | 最后更新时间 | 时间类型 | 每次数据更新时修改为当前系统时间 |

### 业务网 vs 专网

| 字段 | 业务网 | 专网 |
|------|------------|--------------|
| 入库时间 | `REC_CREATE_TIME` | `INDB_TIME` |
| 更新时间 | `REC_LAST_UPDATE_TIME` | `UPDATE_TIME` |

# 四、字段类型约束

## 4.1 数值类型

| 规则 | 说明 |
|------|------|
| 业务含义是数值的应用**数值类型存储**，不得使用字符类型 | |
| 整数**不得使用 DECIMAL** 等带小数数值类型 | |
| 带小数数值类型应**指定长度及精度位数** | `DECIMAL(10,2)` |

## 4.2 字符类型

| 规则 | 说明 |
|------|------|
| **应使用 VARCHAR**，不得使用 CHAR | |
| 不得大量使用 `VARCHAR(4000)`、`VARCHAR(MAX)` 类型 | |

## 4.3 大字段类型

| 规则 | 说明 |
|------|------|
| **不得使用 LONG 类型** | |
| 审慎使用 TEXT、BLOB 等大字段类型 | |
| 确需使用 TEXT/BLOB，**应分离到单独表存储** | |
| 视频、音频、图片等**不得存入数据库**，仅存元数据及路径 | |

## 4.4 时间类型

| 规则 | 说明 |
|------|------|
| 涉及日期、时间的字段应为**日期型**，不得定义为字符型 | |

## 4.5 关联字段

| 规则 | 说明 |
|------|------|
| 多表联查的关联字段，其**数据类型应相同** | |

# 五、字段约束

## 5.1 字段个数

| 规则 | 说明 |
|------|------|
| 单表字段数应 **< 200 个** | |
| 单张表中字符型字段累加 **≤ 8092 字节**（大字段除外） | |

## 5.2 字段注释

| 规则 | 说明 |
|------|------|
| 每张表应有**中文注释**，标明表的含义和用途 | |
| 每个字段应包含**中文注释**，注释内容不得与字段名称一样 | |
| 枚举值字段注释需列出所有枚举内容 | `01代表xxx，02代表xxx` |
| 枚举值 > 5 个且可能追加，应**参数化、设计为单独参数表** | |
| 如字段值包含编码规则，注释中应**标明编码规则** | `前4位代表申报年份` |
| 如表从其他系统获取，字段变化应在注释中**体现** | |

# 六、索引约束

## 6.1 应建索引的字段

| 场景 | 说明 |
|------|------|
| SELECT/WHERE 条件 | 包含在 SELECT、UPDATE、DELETE 语句的 WHERE 条件中的列 |
| 排序/分组 | 包含在 ORDER BY、GROUP BY、DISTINCT 的字段 |
| 联接字段 | 多表链接 JOIN ON 的字段 |

## 6.2 禁止建索引

| 规则 | 说明 |
|------|------|
| **不得使用函数索引** | |
| **不得使用位图索引** | |
| **不得在选择性低的列建单列索引** | 如：性别字段 |
| **不得对每列都建单列索引** | |
| **不得在大字段类型列建索引** | TEXT、BLOB、VARCHAR(4000) |

## 6.3 组合索引规范

| 规则 | 说明 |
|------|------|
| 查询频繁、选择性好、**等值查询的列放在左侧** | |
| 组合索引、单列索引**不得重复建设** | 已建 (A,B) 则不需再建 A 的单列索引 |
| **字段不超过 5 个** | |
| **不得在 OR 条件列上建组合索引** | |
| **有排序需求的列紧跟在等值条件列后面** | |

# 七、数据库约束（禁止使用）

| 禁止项 | 说明 |
|--------|------|
| **外键** | 增加表耦合度，影响高并发性能 |
| **触发器** | 隐式执行，调试困难，难以排查 |
| **临时表** | 资源消耗大，生命周期管理复杂 |
| **EVENT** | 定时任务应在应用层管理 |
| **DBLINK** | 高耦合，跨库事务无法保障 |

---

# 八、ER图约束

| 规则 | 说明 |
|------|------|
| **明确实体** | ER图中每个实体应对应一个物理表，实体名应为物理表的英文表名 |
| **详细属性** | 每个实体至少包括主键及该表与其他表存在关联关系的字段 |
| **关系清晰** | 应明确标注实体之间的关系（一对一、一对多、多对多） |
| **逻辑分组** | 使用不同颜色、边框或区域区分不同业务模块或子系统 |

# 九、数据库设计红线汇总

```
┌─────────────────────────────────────────────────────────────────┐
│                           红线警告                              │
├─────────────────────────────────────────────────────────────────┤
│  ❌ 保留字/关键字作为对象名        ❌ 双引号包裹命名              │
│  ❌ 汉语拼音/首字母缩写            ❌ 单独使用时间戳作为主键       │
│  ❌ LONG 类型                      ❌ 函数索引/位图索引           │
│  ❌ 外键/触发器/临时表/EVENT       ❌ 在大字段上建索引             │
│  ❌ 视频/音频/图片存入数据库       ❌ 字符类型存储数值             │
│  ❌ 整数使用 DECIMAL 类型          ❌ DATE/TIME 字段定义为字符型   │
│  ❌ 单表字段数 ≥ 200              ❌ 字符型字段累加 > 8092 字节    │
│  ❌ 无表/字段中文注释              ❌ 选择性低的列建单列索引       │
└─────────────────────────────────────────────────────────────────┘
```
